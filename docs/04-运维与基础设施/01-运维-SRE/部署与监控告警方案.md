## 1. MVP 管理面最小部署单元

单一管理节点（或 3 台小规格 VM），所有组件以 podman pod / compose 交付，离线镜像包一次导入：

| 组件 | 副本 | 建议资源 | 持久化 | 可降级 |
| --- | --- | --- | --- | --- |
| Nginx + Web 静态资源 | 1 | 0.5C / 512M | 否 | 否 |
| Server（Golang） | 1（可 2） | 2C / 2G | 否（无状态） | 否 |
| PostgreSQL | 1 | 2C / 4G / 50G | **是** | 否 |
| NATS JetStream | 1 | 1C / 1G / 20G | **是** | 否 |
| VictoriaMetrics + vmalert | 1 | 2C / 4G / 100G | **是** | 是 |
| 日志系统 | 1 | 1C / 2G / 50G | **是** | 是 |
| Alertmanager | 1 | 0.5C / 512M | 否 | 是 |
| Grafana | 1 | 1C / 1G | 是（面板配置） | 是 |
| 镜像仓库 | 0（优先对接客户现有） | — | 是 | 是 |

**合计 ≈ 10C / 15G / 220G**，单节点起步。V1 再引入 HA（PG 主从、JetStream 3 节点、Server 多副本、VM 双副本）。

> 如果客户已有 Prometheus/Grafana/镜像仓库，**优先复用而非自带**，这是压缩 B1 的最有效手段。

## 2. 网络与端口

| 链路 | 方向 | 端口 | 说明 |
| --- | --- | --- | --- |
| 浏览器 → 管理面 | 入站 | 443 | 唯一对外端口 |
| Agent → Server | **出站** | 443 | 被管节点无需开放任何入站端口 |
| Server → PG / 队列 / VM / 日志 | 内网 | 内部 | 不暴露 |
| 采集 → Ceph mgr / node-exporter | 管理面出站 | 9283 / 9100 等 | 或由 Agent 转发 |
| Alertmanager → Server | 内网 | Webhook | 告警入库 |
| 镜像仓库 → 被管节点 | 出站 | 5000/443 | cephadm 拉镜像 |

## 3. 指标采集链路

```
Ceph mgr prometheus 模块（每集群）
node-exporter（每节点）
ceph-exporter / Agent 自报指标
   → vmagent（scrape 或 remote_write）
   → VictoriaMetrics（保留期建议 90d，降采样）
   → vmalert（Prometheus 兼容规则）
   → Alertmanager（分组 / 抑制 / 通知）
   → Server Webhook → 告警中心（关联 cluster / region）
   → Grafana（经 Nginx 反代，集群变量由平台注入）
```

**平台自身指标**：API QPS/延迟/错误率、任务成功率与耗时分布、队列积压、Agent 在线率、对账漂移次数、同步周期耗时。

### 3.1 必配告警规则（示例）

| 规则 | 级别 | 说明 |
| --- | --- | --- |
| `CephHealthErr` | critical | 任一集群 `HEALTH_ERR` 持续 2m |
| `CephHealthWarn` | warning | 持续 10m |
| `CapacityHigh` | warning | 使用率 > 80%，critical > 90% |
| `OsdDown` | critical | OSD down 持续 5m |
| `AgentOffline` | warning | 单节点离线 2m；大面积离线升级 critical |
| `TaskFailureRate` | warning | 5m 内失败率 > 20% |
| `QueueBacklog` | warning | 积压 > 阈值持续 10m |
| `ReconcileDrift` | warning | 同一集群连续 3 次对账漂移 |
| `CredentialExpiring` | warning | 凭据临近过期 |
| `ComponentDown` | warning/critical | 按核心/可降级分级 |

> **规则与面板必须纳入版本库并随平台发布**；Ceph 升级后跑指标名回归，防止「指标改名 → 面板空白、告警静默」（权衡分析 B8）。

## 4. 日志链路

| 类 | 内容 | 去向 | 保留 |
| --- | --- | --- | --- |
| 任务步骤日志 | 每步 stdout/stderr、耗时 | 日志系统，`log_ref` 入 DB | 30d |
| Agent 运行日志 | 心跳、任务领取、验签失败 | 日志系统 | 30d |
| 平台访问日志 | Nginx + Server，含 `trace_id` | 日志系统 | 30d |
| 审计日志 | 不可篡改操作记录 | **独立存储（PG 分区表）** | ≥180d |

全链路统一携带 `trace_id / task_id / cluster_id / step_seq`，支持「一次任务 → 步骤 → 节点日志」下钻。日志脱敏规则：凭据、keyring、token、Authorization 头一律打码。

## 5. 备份与恢复（DBA 协同）

| 对象 | 策略 | 恢复目标 |
| --- | --- | --- |
| PostgreSQL | 每日全量 + WAL 归档 | RPO ≤ 5min，RTO ≤ 30min |
| 队列持久化目录 | 随主机快照 | 任务不丢 |
| 凭据加密密钥 | **独立离线备份**（丢了等于全部凭据不可用） | 必须可恢复 |
| 配置 / 面板 / 规则 | 版本库为准 | 随发布 |
| 镜像制品 | 离线包多副本留存 | 可重建 |

**每季度做一次恢复演练**，并验证「平台全停 → 恢复 → 状态自动追平」链路（对应测试用例 TC-19）。

## 6. 故障处置 Runbook

| 现象 | 首判 | 处置 |
| --- | --- | --- |
| 控制台显示不可达 | 区分「Ceph 挂了」还是「管理面/网络挂了」 | 直接 `ceph -s` 或 Ceph Dashboard 交叉验证；**永远不只看平台页面** |
| Agent 大面积离线 | 证书过期 / Server 不可达 / 网络策略变更 | 查证书有效期 → 查 Server 健康 → 熔断任务下发，避免误判后批量重试 |
| 任务积压 | 队列消费慢 / 某任务卡住 | 看 consumer 并发与死信，暂停派发；不要盲目扩容 consumer（可能重复执行） |
| 状态漂移持续 | Ceph 被平台外修改 / 对账失败 | 以 Ceph 为准，检查平台外变更记录，禁止平台自动「纠正」 |
| 告警静默 | 规则/指标名/链路问题 | 从 exporter → VM → vmalert → Alertmanager 逐段验证，勿直接认定「集群正常」 |
| 管理面全停 | 主机/存储故障 | **先确认数据面 IO 正常**（G1）；再恢复控制面；无需紧急慌乱 |
| 疑似入侵 | 安全事件 | 立即触发全局熔断、吊销证书、保留现场（见[安全设计 §7](../../02-研发/08-安全工程师/安全与审计设计.md)） |

## 7. 容量与规模

- 20 集群 / 500 节点时，默认 30s 同步周期会产生约 1000 次/分钟的状态查询 → 必须按集群分片 + 抖动（jitter），并对 `ceph -s` 设置缓存与限流（B13）。
- 指标采样间隔 30s，单节点约 2k~5k series，按需估算 VM 磁盘；启用降采样保留长期趋势。
- 同步周期、并发上限、队列 consumer 数全部配置化，不写死。
