## 1. 决策

| 层 | 选择 | 部署方式 |
| --- | --- | --- |
| 指标 | VictoriaMetrics + vmalert | 自建，单节点（MVP） |
| 告警 | Alertmanager | 自建，单节点 |
| 日志 | **VictoriaLogs** | 自建，单节点 |
| 面板 | Grafana（经反代统一鉴权） | 自建 |

**全部自建、默认安装**，不依赖客户环境。

## 2. 理由

1. **同一套栈、同一套查询习惯**：VM 与 VictoriaLogs 同属 VictoriaMetrics 家族，PromQL / LogsQL 的运维心智一致；离线包也只需维护一套版本节奏。
2. **告警不外包**：如果接客户 Prometheus，平台自身 SLO 就受客户可用性与权限牵制——管理面挂了而告警也发不出来，是最糟的组合。
3. **开箱可用**：对私有化客户，「装完就有监控面板」比「你自己接一下 Prometheus」更有说服力（ADR-13 放宽 G6 后，这是可以正面主张的卖点）。
4. **与既有约束一致**：指标不入 PG（ADR-06/I9）、Grafana 必须走反代（ADR-09/I8），这两条在新栈里都保持不变。

## 3. 代价

| 代价 | 说明 |
| --- | --- |
| 组件数量 | 4 类组件（VM/vmalert、Alertmanager、VictoriaLogs、Grafana），管理面资源与离线包体积上升 |
| 生态差异 | VictoriaMetrics 与 Prometheus 规则有边界差异（B8）；VictoriaLogs 的查询语法与社区案例比 Loki/ELK 少 |
| 双告警源风险 | vmalert 与 Grafana Alerting 都能告警，必须只保留一条规则链路，否则同一条告警会发两次 |

## 4. 与 ADR-13「可选装配」的关系

ADR-13 说「可观测性可选装配」，本 ADR 说「默认自带」——两者不冲突，落地方式是：

- **默认全装**（保证开箱可用）；
- **打包分层**（核心包 / 可观测包 / 仓库包），客户明确不要日志时可只搬核心包，体积与组件同步减少。

即：默认体验完整，裁剪是选项而非前提。

## 5. 约束

| 约束 | 原因 |
| --- | --- |
| 只有一条告警规则链路（vmalert） | 避免双发；Grafana 只做面板，不开 Alerting |
| 日志保留 30 天，审计保留 ≥180 天 | 两类数据生命周期不同，**不能都塞进日志系统**（审计在 PG，ADR-06） |
| VictoriaLogs 必须配磁盘水位告警 | 日志增长比指标快，最先打满盘的通常是它 |
| 面板必须经反代鉴权 | 直连 Grafana 会绕过平台 RBAC（B9） |
| 离线包内固定版本与 digest | 三个组件都要进 BOM，禁止浮动 tag |

## 6. 风险

| 风险 | 缓解 |
| --- | --- |
| VictoriaLogs 生态案例少，排障缺参考 | 关键查询写成 runbook；保留 Loki 作为备选，切换只涉及采集端与查询 |
| VM 与 Prometheus 规则不兼容处踩坑 | 规则 CI 校验 + 指标回归（B8 缓解项） |
| 组件多导致资源超预算 | 部署方案已按 14C/22G/300G 估算；可观测包可裁 |
| 客户强制统一用他们的 Prometheus | 允许「指标双写」（remote_write 同时给客户），但不把客户实例作为平台唯一数据源 |

## 7. 什么情况下推翻

- 客户明确要求并入其统一可观测平台，且愿意提供稳定实例与权限 → 改为集成模式（保留自有 VM 作为兜底）。
- VictoriaLogs 在目标规模下性能或稳定性不达标 → 换 Loki（采集端只需换 shipper）。

推翻流程同前：新开 ADR → 本 ADR 标 `Superseded` → 同步架构设计 §4.1、部署资源表、PRD FR-08/09、安装手册 BOM、`AGENTS.md` §1。
