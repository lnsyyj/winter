## 1. 决策

Agent **不以 root 运行**：

- 以专用系统账号（如 `winter-agent`）常驻，自身只做「拉任务、验签、调度、上报」；
- 需要特权的动作通过 **sudoers 精确白名单**执行，规则精确到「绝对路径命令 + 允许的参数形态」；
- `NOPASSWD` 仅对白名单条目生效，**禁止** `ALL`、禁止通配符参数、禁止 shell 解释；
- cephadm / podman 相关操作若必须特权，走同一白名单，不额外开 root。

## 2. 理由

1. **B2 的唯一有效缓解是「缩小可执行集合」**：把 root 藏起来只是掩耳盗铃，白名单才是真正的边界。
2. **爆炸半径可量化**：root 意味着「管理面被攻破 = 全部节点 root」；白名单意味着「最多执行到白名单内的命令」，且每条都可审计。
3. **审计可交叉核对**：sudo 自身有日志（`/var/log/secure`），与平台审计两边比对，能发现「绕过平台直接调 sudo」的行为（B11 的旁路审计问题）。
4. **与本项目已有约定一致**：I4 早就规定「命令白名单 + 强类型参数 + `exec argv`，禁止自由 shell」，本条是把 I4 从「平台内约束」延伸到「操作系统层约束」。

## 3. 代价与必须处理的细节

| 项 | 影响 | 处理 |
| --- | --- | --- |
| sudoers 维护成本 | 每新增一类任务要同步改白名单 | 白名单模板随 role/任务类型版本化，与代码同仓库评审 |
| 参数形态校验 | sudo 只认命令与前缀，不认语义 | 平台侧仍做参数校验（I4），sudo 只是第二道门 |
| cephadm 少数操作要求 root | 可能直接失败 | 用 `sudo <绝对路径> cephadm ...` 包一层；仍不行则单条评估、写进安全评审 |
| podman socket 权限 | Agent 需拉起容器时权限不足 | 授予专用组访问 podman（或 rootless + `--privileged` 的替代方案），逐场景确认 |
| `secure_path` 与变量 | sudo 会清空环境，命令找不到依赖 | 一律使用绝对路径；必要时在 sudoers 里显式 `setenv` 白名单 |
| 白名单过宽 = 等价 root | 例如允许 `sudo bash`、`sudo tee /etc/*` | 评审红线：禁止解释器、禁止写入系统配置目录 |

## 4. 验收（可测）

| 标准 | 判定 |
| --- | --- |
| 越界命令被拒 | 构造白名单外命令，sudo 返回失败且平台记录拒绝事件（TC-27） |
| 无 root 常驻 | `ps -o user= -p <agent_pid>` 为专用账号 |
| 白名单可审计 | 每条 sudoers 条目能对应到一个任务类型；无孤儿条目 |
| 变更需评审 | sudoers 改动必须走 MR + 安全评审，且产生审计记录 |

## 5. 风险

| 风险 | 缓解 |
| --- | --- |
| 白名单过窄导致功能不可用（B12） | 按任务类型逐步放开；每次放开记录理由；用「该任务是否真的必需」做准入 |
| 团队为省事直接加 `ALL` | 评审红线 + 定期扫描 sudoers（CI 检查禁止 `ALL` 与通配） |
| 不同 OS 的 sudo 版本行为差异 | 锁定 CentOS Stream 9 自带版本，写入兼容矩阵（D10） |
| 特权操作分散在多处 | 统一收敛到一个 `winter-priv` 包装脚本，sudoers 只允许它 |

## 6. 什么情况下推翻

- 目标客户的合规要求「服务必须 root 运行」（少见但存在），且无法用 capability 拆分 → 需安全评审后例外放行，并在文档中标注风险等级。
- podman 的 rootless 能力演进到可完全替代 sudo 白名单 → 可简化为纯用户态，但白名单思路不变。
