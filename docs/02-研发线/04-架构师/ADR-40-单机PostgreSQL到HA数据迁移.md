## 1. 问题

ADR-39 打通了「单节点 HA 引导态 → 3 节点」的在线扩容，但把 **MVP 单节点** 升级到 HA 仍有断点：

- 单节点 `deploy` 用系统 PostgreSQL：端口 `5432`，数据目录 `/var/lib/pgsql/17/data`，库 `winter`。
- HA `postgresql-ha` 用独立集群：Patroni `5433`、HAProxy 入口 `5434`，数据目录 `/var/lib/pgsql/17/ha`，库 `winter`。

两者数据目录完全独立。直接跑 `postgresql-ha` 会在 5433 上建**空库**，Server 连接串切到 5434 后，原 5432 里已写入的业务与审计数据对应用不可见。需要一个**生产级、可回滚、可校验**的迁移 stage 把数据从源实例搬到 HA 集群。

## 2. 关键事实（决定了迁移范围）

- 业务表与审计表在**同一个 `winter` 库**：`config.go` 里 `AUDIT_DATABASE_URL` 缺省回退到 `DATABASE_URL`，审计 migration（`audit_intents` / `audit_results`，ADR-29 链式哈希）与业务 migration 都由 Server 启动时对同一库执行。因此**只需搬一个库**。
- 表的创建由 Server 启动时的 embed migration 完成（`create ... if not exists`）。所以迁移可以走两条路：
  1. **物理迁移**（pg_dump -Fc + pg_restore）——保留全部数据、序列、约束，推荐；
  2. 只搬数据行，让 Server 重建表——丢失非表对象（函数/触发器/权限），不采纳。
- 单节点与 HA 的库名/角色名一致（`winter` / `winter`），省去重命名。

## 3. 决策

新增 `postgresql-migrate` stage，把 5432 源库的 `winter` 库迁移到 5433 HA 集群。按**允许停机窗口**设计（用户明确：迁移期间可以停服等待，但扩容控制面必须具备此能力），采用保守的停止世界方案换取强一致：

### 3.1 流程（严格有序，任何一步失败即中止且不切换流量）

1. **前置校验（只读）**：源实例 5432 可达且含 `winter` 库；目标 HAProxy 5434 可达且 Patroni 报告 primary；目标 `winter` 库为空（无业务表）或已标记「已迁移」；两端 PG 大版本兼容；磁盘剩余空间 > 源库 1.5 倍。
2. **进入维护窗口**：停止 `winter-server`（所有副本），确认无活跃连接；记录当前时间点为回滚锚点。
3. **源库一致性快照**：用 `pg_dump -Fc --no-owner --no-acl`（自定义格式、并行友好）经本地 socket peer 认证导出，避免密码出现在命令行/日志。
4. **目标库恢复**：`pg_restore` 到 HA primary 的 `winter` 库；因表已由 Server migration 建好，用 `--clean --if-exists` 或先落到相同结构，需保证幂等。
5. **数据校验**：逐表比对行数（源 vs 目标），并对关键表（users / clusters / tasks / audit_intents / audit_results）做 `md5(string_agg(...))` 或分页 checksum；不一致即中止并保持 Server 停机。
6. **切换流量**：幂等写入「已迁移」标记；确认 Server env 指向 HA 入口（5434）；启动 Server，跑 `/healthz` 与业务库读探针。
7. **退出维护窗口**：校验通过后才删除临时 dump 文件；**源 5432 数据目录保留不删**，作为回滚兜底（手工清理另行决定）。

### 3.2 幂等与回滚

- stage 可重复执行：检测到「已迁移」标记 + 校验通过 → 直接跳过数据搬运，只做校验与探针（快速恢复态）。
- 回滚：迁移失败且 Server 仍停机时，把 Server env 连接串指回 5432、重启即可；源库从未被修改。成功切换后的回滚属于「回退到旧集群」，需另行停 HA、启 5432 并切回——本 stage 不自动做，但在输出中打印回滚命令。
- 目标库非空且无标记时**拒绝执行**，防止覆盖未知数据。

### 3.3 与其他 stage 的关系

- 前置条件：`postgresql-ha` 已在目标节点建成 HA 集群（至少单节点 HA 引导态）；本 stage 不负责建集群。
- 后续：`application-ha`（多副本 Server）、`postgresql-scale-out`（扩到 3 节点）在迁移完成后进行。
- 与 ADR-39 的分工：ADR-39 处理「HA 集群内部 1→3 的在线扩容」；本 ADR 处理「MVP 单机的存量数据进入 HA」。

## 4. 为什么这样设计

| 备选 | 为什么放弃 |
| --- | --- |
| 逻辑同步（双写 / CDC） | 控制面组件复杂度高，项目无 MQ（ADR-36），运维面陡增；用户允许停机窗口，不值得 |
| 只搬数据行、Server 重建表 | 丢函数/触发器/约束/序列当前值，审计链哈希上下文可能断裂 |
| 边迁移边服务 | 一致性与冲突处理复杂；用户明确可停机，停止世界最稳 |
| 迁移后删除源库 | 失去唯一回滚兜底；清理应是独立的、人工确认的操作 |
| 密码写进 pg_dump 命令行 | 泄露到进程列表与日志：`PGPASSWORD` 环境变量 + 本地 socket peer 认证 |

## 5. 影响

| 对象 | 变化 |
| --- | --- |
| `playbooks/postgresql-migrate.yml`（新增） | 迁移 stage 编排与前置校验 |
| `deploy.sh` | 新增 `postgresql-migrate` stage 入口 |
| `group_vars/all.yml` | 新增 `pg_migrate` 配置块（源/目标端口、库名、校验开关、标记路径） |
| Server env | 修复单节点 HA 引导态下连接串误连 5432 的推导 bug（见实现） |
| 运维手册 / README | 补充升级流程与停机窗口说明 |

## 6. 关键约束

- **迁移期间控制面停机**，需在维护窗口执行；大库时间随数据量线性增长。
- 源库在迁移成功后**保持原样**，不自动删除——这是回滚能力的根基。
- 校验失败时宁可保持停机也不切换流量；运维须人工介入。
- 密码严禁落盘/落日志；dump 临时文件权限 0600，成功后删除。

## 7. 风险

| 风险 | 缓解 |
| --- | --- |
| 迁移中 Server 崩溃导致半状态 | 前置/切换分离；未写「已迁移」标记前可安全重试 |
| 目标库被误判为空导致覆盖 | 非空且无标记直接拒绝 |
| 审计链哈希跨库失效 | 审计表随库整体迁移，数据与哈希原样保留；校验覆盖 audit 表行数 |
| 大库磁盘不足 | 前置校验剩余空间 > 源库 1.5 倍 |
| 版本不兼容导致 restore 失败 | 前置校验 PG 大版本一致；失败即中止、源库无损 |

## 8. 什么情况下推翻

- 引入 CDC/逻辑复制组件且运维能力到位，可改为在线迁移，则本 ADR 的停机约束失效。
- 项目取消 MVP 单节点形态（首次部署即 HA），不再存在 5432 存量库，本 stage 失去意义。

推翻流程：新开 ADR → 本 ADR 标 `Superseded` → 同步架构设计、部署手册与 `docs/README.md` 索引。
