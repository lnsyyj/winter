## 1. 决策

保留期做成**配置项**，但给默认值、下限与容量校验：

| 数据 | 默认 | 下限 | 上限 | 超过在线期后 |
| --- | --- | --- | --- | --- |
| 日志（VictoriaLogs） | 30 天 | 7 天 | 180 天 | 直接删除 |
| 指标（VictoriaMetrics） | 30 天 | 15 天 | 365 天 | 直接删除 |
| 任务与步骤记录（PG） | 90 天 | 30 天 | 365 天 | 归档摘要后删明细 |
| 审计（独立库） | **在线 180 天** | **180 天（不可下调）** | 730 天 | 按月归档，归档保留 12 个月 |
| 会话（PG） | 7 天 | 1 天 | 30 天 | 删除 |

**审计的 180 天是硬下限**：这是合规底线，不是性能参数；其余各项都可以按客户磁盘情况调整。

## 2. 配置形态

```yaml
platform:
  retention:
    logs_days: 30
    metrics_days: 30
    tasks_days: 90
    audit_online_days: 180      # 低于 180 直接拒绝启动
    sessions_days: 7
    # 容量评估用的估算参数（用于把"天数"换算成"磁盘"）
    daily_log_ingest_gb: 2
    series_per_node: 1500
```

配套三档预设（写在文档里，不是代码分支）：**精简**（7/15/30/180）、**标准**（30/30/90/180）、**长留**（90/90/365/730）。

## 3. 为什么必须做容量校验

保留期是「天数」，磁盘是「GB」，中间隔着日增体积与 series 数。客户把日志从 30 天调到 180 天，磁盘需求直接 ×6——如果没人拦，结果是**六个月后磁盘满、平台不可写**。

因此：

1. `prechecks` / `post-deploy` 按配置估算所需磁盘，与可用空间比对，超出即**告警并给出建议值**；
2. 修改保留期必须走 `reconfigure`，并在输出里打印「本次变更后的估算占用」；
3. 磁盘水位 80% 告警、90% 时平台进入「只读保护」（拒绝新的写任务而不是让 PG 崩）。

## 4. 清理实现约束

| 约束 | 原因 |
| --- | --- |
| 按分区 `DROP`，不用大事务 `DELETE` | 逐行删会锁表、膨胀 WAL，清理任务本身变成事故 |
| 清理任务每日 03:00，单次有上限 | 避免一次清太多拖垮 IO |
| 清理动作**写审计**（元审计） | 谁在何时删了什么范围的数据，必须可查 |
| 归档先验证可读，再删在线数据 | 顺序反了就是数据丢失 |
| 会话清理与过期清理分开 | 会话是高频小表，不必等日任务 |

## 5. 数据模型影响

| 对象 | 变更 |
| --- | --- |
| `tasks` | 归档后保留摘要：`id/type/status/created_by/started_at/finished_at`，删除 `params_jsonb` 与 `task_steps` 明细 |
| `clusters` | 新增 `drift_state`（ok/drift）、`last_drift_at` —— 补齐 §5.3 提到但模型里一直缺的字段 |
| 审计库 | 按月分区；归档为 `audit-YYYYMM.tar.zst` + 校验和，索引清单留在库里 |

## 6. 代价

| 代价 | 说明 |
| --- | --- |
| 三档预设容易被当成「随便选」 | 文档需明确：档位要与磁盘匹配，改动前先看估算输出 |
| 容量估算本身是估算 | 以实际水位告警为准；估算只用于拦截明显不合理的配置 |
| 归档检索变慢 | 归档需先恢复单月，接受这个代价（在线 180 天已覆盖绝大多数审计查询） |
| 任务明细归档后不可查步骤日志 | 因此日志保留期建议 ≥ 任务保留期中「最近一次故障复盘窗口」 |

## 7. 风险

| 风险 | 缓解 |
| --- | --- |
| 客户把审计调到 180 以下「省空间」 | 配置校验直接拒绝启动，并在错误信息里说明合规原因 |
| 保留期调大后磁盘满 | 容量校验 + 水位告警 + 只读保护三道闸 |
| 清理任务误删（分区名算错） | 清理前校验分区边界与当前时间，干跑模式（`--dry-run`）先输出将删除的分区 |
| 归档文件损坏 | 归档后立即校验 sha256，并抽样解包 |

## 8. 验收（TC-38）

| 场景 | 通过标准 |
| --- | --- |
| 默认配置 | 各表/索引按默认天数清理，边界正确（不多删一天、不少删一天） |
| 审计下限 | 把 `audit_online_days` 设为 90 → 启动被拒，错误信息说明合规下限 |
| 容量校验 | 把日志调到 180 天 → 估算超限时给出告警与建议值 |
| 干跑 | `--dry-run` 输出将删除的分区清单，不实际删除 |
| 不可写保护 | 磁盘压到 90% → 新写任务被拒并给明确原因，读操作正常 |
| 元审计 | 每次清理都产生一条审计记录（范围、条数、耗时） |

## 9. 什么情况下推翻

- 客户要求「审计永久在线」→ 需要独立归档存储与检索方案，不能靠 PG 分区硬扛。
- 引入冷热分层存储 → 保留期策略从「删」改为「降层」，本 ADR 的参数结构可保留。

推翻流程同前：新开 ADR → 本 ADR 标 `Superseded` → 同步架构设计 §8/§12、部署方案、`group_vars`、TC-38。
