## 1. 目标与结论

| 项 | 值 |
| --- | --- |
| 设计规模 | **10,000 节点 / 100 集群 / 单 Region**（**单控制面上限**；>10k 走 [ADR-38](ADR-38-Agent通信分片.md) 的 20 片方案） |
| 单副本连接上限 | **5,000**（留 50% 余量） |
| 10k 所需副本数 | **3**（2 个跑满 + 1 个冗余，滚动发布不断服） |
| 心跳 | 10s，离线阈值 30s，**落库批量 30s** |
| 任务派发 | 推送为主（长连接）+ 60s 兜底对账，**不轮询** |

**核心结论：单副本能扛 10k 连接，但不该这么用**——瓶颈不在连接数，而在心跳写库、多副本任务路由、重连风暴、证书到期集中这四件事。

## 2. 容量模型（可算）

| 资源 | 公式 | 10k 时的值 |
| --- | --- | --- |
| 连接内存 | 连接数 × 100 KB | ≈ 1.0 GB（RSS 约 2–3 GB） |
| 心跳消息 | 连接数 ÷ 10s | 1,000 msg/s（Go 无压力） |
| 心跳落库 | 连接数 ÷ 30s | ≈ 333 行/s（批量 unnest 一次写完） |
| 文件描述符 | 连接数 + 余量 | 需 `ulimit -n ≥ 65535` |
| conntrack 条目 | 连接数 × 1.2 | 需 `nf_conntrack_max ≥ 131072` |
| 对账采集 | 集群数 ÷ 30s | 3.3 次/s（**每集群只选一个节点**） |
| 任务派发 | 按操作批次限速 | 默认 ≤100 任务/s |

> **每连接 100 KB 的构成**：goroutine 栈 8 KB（可增长）、TLS 读缓冲 ~40 KB、应用读写缓冲 ~40 KB、连接与状态结构 ~10 KB。这是可被压测验证的假设，压测若超出即回头改预算。

## 3. 四个必解问题

### 3.1 心跳不能每拍写库

| 做法 | 后果 |
| --- | --- |
| 每次心跳 `UPDATE last_seen_at` | 1,000 写/秒，PG 一半预算没了 |
| **内存更新 + 30s 批量 flush**（本 ADR） | 333 行/s，一次事务批量写完 |

批量 SQL 形态：`UPDATE hosts h SET last_seen_at = v.t FROM unnest($1::uuid[], $2::timestamptz[]) AS v(id, t) WHERE h.id = v.id`。

**离线判定也不查库**：内存里存 `agent_id → last_seen`，每秒扫描 1/30 分片（10k/30 ≈ 333 条），超 30s 的标记 offline 并推事件。DB 只是持久化落点，不是判定依据。

### 3.2 多副本的任务路由（删掉 MQ 后暴露的新问题）

Server 多副本时，任务可能被副本 A 领到，而目标 Agent 连在副本 B——**A 推不到它**。

| 方案 | 评价 |
| --- | --- |
| **a. 每个副本只领「本地有连接」的 Agent 任务**（采用） | 用临时表 join 本地连接列表：`WHERE t.target_agent_id IN (SELECT id FROM local_conns)`。简单、无跨副本通信；代价：Agent 迁移到别的副本后，旧任务要等租约回收 |
| b. 路由表（agent → replica）存 PG，领到后转发 | 精确，但要处理副本重启后的路由失效，且引入跨副本 RPC |
| c. 回到 MQ | 与 ADR-36 冲突，不采用 |

**配套**：租约到期（`leased_until`）仍由**任意副本**回收置为 `PENDING`，保证「Agent 迁移」不会让任务永久滞留；回收后由当前持有连接的副本接手。

### 3.3 重连必须是「抖动 + 限速」

Server 重启 = 10k 同时重连。按 1 ms/次握手算，单核 10 秒；叠加 TLS 1.3 session ticket 可降到 1–2 秒，但仍是「一次发版瘫 30 秒」。

| 措施 | 值 |
| --- | --- |
| 客户端抖动 | 0–300s 随机（不是固定间隔） |
| 退避 | 1s→2s→4s→…→上限 300s，加 ±30% 抖动 |
| 服务端 accept 限速 | 200 连接/秒（超出排队，不拒绝） |
| TLS 会话恢复 | ticket 开启，握手成本降一个量级 |
| 发布策略 | 滚动重启，一次只换一个副本；禁止同时重启 |

**验收标准**：3 副本、10k 节点、全量重启 → **5 分钟内连接恢复 99%**。

### 3.4 证书到期不能同日

10k 台一次性预装，若同一时刻签发 → 90 天后同一天 10k 台一起轮换，又是一次自我 DDoS。

| 措施 | 值 |
| --- | --- |
| 签发抖动 | 有效期 90 天 ±7 天（ADR-28 已定，这里强调**必须在预装时逐台生效**） |
| 预装分批 | 每批 ≤500 台，批次启动时间打散（不并发签完） |
| 轮换错峰 | 每个 Agent 在「到期前 30 天」内的随机时刻发起 |
| 监控 | 每日到期数 >200 即告警（防尖峰） |

## 4. 采集不能每节点都做

10k 节点若每台都跑 `ceph -s` 上报 → 333 次子进程/秒，纯属浪费。

**规则**：**每个集群只选一个采集代表**（collector host），由该节点执行 `ceph -s` / 拓扑查询，结果经 Agent 上报。

| 项 | 做法 |
| --- | --- |
| 选举 | 优先 `hosts.labels` 标记 `collector=true`；未标记时取 `agent_id` 哈希最小的在线节点 |
| 失效切换 | 采集代表离线 >30s → 重新选举（不落库，内存计算，避免状态漂移） |
| 采集周期 | 30s/集群（100 集群 = 3.3 次/s） |
| 例外 | `limited` 只读档集群同样适用（Agent 仍执行只读查询，只是权限受限） |

## 5. 系统参数与反压

| 项 | 值 | 说明 |
| --- | --- | --- |
| `ulimit -n` | ≥65535 | 默认 1024 会直接崩；写进 systemd unit 与容器 limit |
| `net.core.somaxconn` | 4096 | 重连风暴时的排队深度 |
| `nf_conntrack_max` | ≥131072 | 10k 连接的 1.2 倍余量 |
| Server 连接池 | 单副本 ≤20 PG 连接 | 3 副本 ×20 = 60，留足 PG 余量 |
| 派发限速 | 默认 100 任务/s，可配 | 防止批量操作打满 Harbor 与网络 |
| 批量操作 | 自动分批（每批 ≤1000 节点） | 任务表不因一次 10k 行插入而长事务 |

**反压**：当 `PENDING` 数超过阈值（默认 5,000）或最老任务年龄 >10 分钟时，**拒绝新的批量任务提交**，只允许单集群操作。

## 6. 指标与告警阈值

| 指标 | 告警阈值 |
| --- | --- |
| 副本连接数 | > 单副本上限 80%（4,000） |
| 副本间连接偏差 | > 20%（提示负载不均或路由异常） |
| 心跳处理延迟 p99 | > 2s |
| 批量 flush 耗时 | > 1s |
| `PENDING` 数量 / 最老任务年龄 | >5,000 / >10min |
| 每日证书到期数 | >200 |
| 重连速率 | >200/s 持续 1min（可能是风暴） |

## 7. 代价

| 代价 | 说明 |
| --- | --- |
| 3 副本带来路由复杂度 | 3.2 的「本地优先 + 租约兜底」不是零成本，需要额外测试 |
| 心跳不实时可见 | `last_seen` 最多滞后 30s；UI 显示「30 秒内」而非精确到秒 |
| 采集代表机制 | 引入选举逻辑；代表节点故障会有一次 ≤30s 的采集空洞 |
| 限速与反压 | 大批量操作变慢（这是刻意的），运维要有心理预期 |
| 参数依赖 | fd/conntrack/somaxconn 配错就是「连不上」，需写进安装检查 |

## 8. 验收（TC-41）

| 场景 | 通过标准 |
| --- | --- |
| 10k 连接建立 | 10k 模拟 Agent 全部连上；RSS ≤4GB/副本；无 fd 报错 |
| 心跳稳态 | 1,000 msg/s 下 CPU <30%；p99 延迟 <2s；flush 不积压 |
| 全量重连 | 3 副本重启后 **5 分钟内 99% 恢复**；无握手风暴 |
| 任务派发 | 10k 任务按 100/s 派发；无重复派发；`PENDING` 单调下降 |
| 副本迁移 | Agent 断开重连到另一副本，旧任务在租约到期后由新副本接手 |
| 采集收敛 | 100 集群每 30s 各采集一次；同一时刻只有一个节点在执行 |
| 批处理 | 一次提交 10k 节点的批量任务，不产生长事务、不 OOM |
| 证书轮换 | 单日到期数始终 ≤200；无集中失败 |

> **2026-11-15 扩展**：目标规模提高到 100,000 节点时，本 ADR 的单控制面模型不再适用，改为 [ADR-38](ADR-38-Agent通信分片.md) 的「20 片 × 每片 2 副本」。本 ADR 的以下结论仍然有效：单进程 5,000 连接上限、心跳 30s 批量落库、重连抖动、证书打散、每集群一个采集代表。

## 9. 什么情况下推翻

- 目标规模 >10,000 节点或需要跨 Region 自治 → 控制面要分片（按 Region 拆），本 ADR 的单控制面模型不适用。
- 需要「秒级」状态可见性 → 心跳必须每拍落库，届时 PG 需要更大规格或引入时序库承接。
- 需要 10k 并发任务执行 → 派发限速与 Harbor 并发成为硬瓶颈，需要独立的制品分发机制。

推翻流程同前：新开 ADR → 本 ADR 标 `Superseded` → 同步架构设计 §1/§5.2/§9/§10、部署方案、TC-41、售前能力边界。
