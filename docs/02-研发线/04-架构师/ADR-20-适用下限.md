## 1. 决策

**低于 3 套集群或 20 个节点，不推荐部署本平台。**

这是**推荐下限**，不是技术门禁：

- 技术上 1 套集群也能装；
- 但此时「部署 + 运维管理面」的成本高于收益，应直接用 Ansible / Ceph Dashboard。

## 2. 理由

管理面的固定成本是真实的：

| 成本项 | 量级 |
| --- | --- |
| 资源 | ≥14C / 22G / 300G（ADR-16 后的估算） |
| 组件 | 9 类，其中 4 类有状态（PG、RabbitMQ、Harbor、VictoriaLogs/VM） |
| 运维 | 备份、升级、告警响应——一套需要被运维的系统（B1） |

3 套集群 / 20 节点大致是这条成本线被摊平的临界点：低于它，客户自己写 playbook 更省；高于它，多集群统一视图与审计的价值才开始显现。

## 3. 这条决策的四个实际含义

1. **售前必须明示**：能力边界清单里加一条「适用规模」，不允许销售为了签单隐去。
2. **不做「极简版」**：不为了覆盖小客户额外维护第二套部署形态——那是双倍维护成本，且会破坏「一次交付」的一致性。
3. **小客户不是不能碰，而是要换形态**：托管 / SaaS / 共享管理面，属于另一个产品命题，需单独立项。
4. **上限仍开放**：下限解决「太小的不值得」，上限（20 集群 / 500 节点是假设）仍需业务确认（PRD §11.3 第 2 问）。

## 4. 风险

| 风险 | 缓解 |
| --- | --- |
| 销售压力下被突破，为小客户硬上 | 合同与验收口径写明适用规模；实施报价按规模分档，让小单自然不划算 |
| 客户规模处于临界（2 套 / 18 节点） | 由售前做「成本对比」：平台 vs 脚本，用数字说话，不靠话术 |
| 下限写死后，产品失去下探空间 | 下限是「推荐」而非「禁止」；真要下探，走 ADR 修订而不是私下放宽 |

## 5. 什么情况下推翻

- 出现「多租户 / 托管」形态，管理面成本可被多个客户分摊 → 下限自然下移。
- 部署成本因工具链成熟大幅下降（如 ADR-17 框架把实施压到 1 小时内）→ 重新评估临界点。

推翻流程同前：新开 ADR → 本 ADR 标 `Superseded` → 同步 PRD §2.1、售前能力边界、权衡 §5.1、项目计划 RK-1。
