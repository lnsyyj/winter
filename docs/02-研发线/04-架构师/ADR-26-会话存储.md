## 1. 背景

ADR-22 要求会话「服务端可撤销」，但没定存在哪；架构设计 §10 又写着「会话放 JWT/Redis（可选）」。这两句是矛盾的：**JWT 自包含、签发后无法即时撤销**，要撤销只能靠短 TTL 或黑名单，而黑名单又回到「每次查库」。

## 2. 决策

| 项 | 决策 |
| --- | --- |
| 存储 | **PostgreSQL `sessions` 表**，不引入 Redis |
| 令牌形态 | **不透明随机 Session ID**（256bit，base64url），浏览器只拿到它；**不用 JWT 装身份** |
| DB 存什么 | 只存 Session ID 的 **SHA-256 哈希**，不存明文——拖库也无法冒用 |
| 校验 | 每个请求查一次主键（未撤销 + 未过期）；MVP **不加缓存** |
| CSRF | 双提交 token（Cookie 之外的 header），写操作必须带 |
| 多副本 | 天然一致，无需共享缓存 |

## 3. 理由

1. **「立即踢人」是硬需求**：离职、凭据泄露、越权都要马上生效，等 TTL 不是可接受的答案。
2. **平台规模不需要 Redis**：内部管理平台并发很低，一次主键查询的成本可以忽略；为省这一次查询引入第 10 个组件不划算。
3. **不透明 ID 比 JWT 更适合「可撤销」语义**：JWT 把身份塞进令牌，等于把撤销权交给时间。
4. **存哈希而非明文**：数据库是最可能被拖走的东西，存哈希让「拿到库」不等于「拿到会话」。

## 4. 表结构

| 字段 | 说明 |
| --- | --- |
| `id` | 主键（UUIDv7，仅内部引用） |
| `session_hash` | Session ID 的 SHA-256，唯一索引 |
| `user_id` | 关联 `users` |
| `idp` | `local` / `ldap`，便于统计与排障 |
| `created_at` / `last_seen_at` / `expires_at` | 生命周期 |
| `revoked_at` / `revoke_reason` | 撤销审计（登出、管理员踢人、密码变更、权限变更） |
| `client_fp` | UA + IP 哈希，仅记录不强制绑定（移动网络会换 IP，强制绑定误杀率高） |

## 5. 生命周期规范

| 项 | 值 | 说明 |
| --- | --- | --- |
| 绝对过期 | 12h（可配） | 到期必须重新登录 |
| 空闲过期 | 30min（可配） | 无请求即失效 |
| `last_seen_at` 更新 | 节流：间隔 >60s 才写 | 否则每请求一次 UPDATE，纯浪费 |
| 登录后 | **轮换 Session ID** | 防会话固定攻击 |
| 登出 | 置 `revoked_at`，不等过期 | — |
| 管理员踢人 | 支持「踢单个会话」与「踢该用户全部会话」 | 后者用于离职/泄露 |
| 密码或角色变更 | 撤销该用户全部会话 | 权限变了，旧会话不该继续持有旧权限 |
| 清理 | 定时删除过期 >7 天与已撤销 >7 天的记录 | 避免表无限增长 |

## 6. 安全约束

| 约束 | 原因 |
| --- | --- |
| Cookie：`__Host-` 前缀 + `HttpOnly` + `Secure` + `SameSite=Lax` + `Path=/` | `__Host-` 强制 Secure 且禁止 Domain，降低子域注入风险 |
| **禁止把 Session ID 或任意身份 token 放 localStorage** | XSS 可直接读 |
| 写操作校验 CSRF token（双提交） | Cookie 自动携带，必须额外证明「是我们页面发起的」 |
| 登录失败统一提示，限流按「用户名 + IP」跨 provider 计数 | 防枚举与爆破（ADR-22） |
| 审计只记 `session_hash` 前 8 位，不记完整 ID | 完整 ID 等于可冒用的凭据 |
| 响应头加 `Cache-Control: no-store` | 避免中间层缓存鉴权响应 |

## 7. 代价与风险

| 项 | 说明 |
| --- | --- |
| 每请求一次 DB 查询 | 内部平台可接受；若将来 QPS 上升，加缓存**必须**保证撤销即时生效（版本号 + 每请求校验），否则宁可不加 |
| PG 抖动 = 全员掉线 | 监控会话查询延迟与错误率；PG 是核心依赖，不属可降级组件（与监控/日志不同） |
| 长会话表增长 | 清理任务必须实现，否则三年后这张表成负担 |

## 8. 验收（TC-32）

| 场景 | 通过标准 |
| --- | --- |
| 登出 | 同一 Session ID 立即失效 |
| 管理员踢人 | 目标会话下一个请求即 401，其他会话不受影响 |
| 角色变更 | 该用户全部会话被撤销 |
| 会话固定 | 登录前后 Session ID 不同 |
| 空闲过期 | 超时后请求 401 并提示重新登录 |
| 拖库模拟 | 库里只有哈希，无法据此重建可用 Cookie |
| 多副本 | 在 A 副本登录、B 副本请求正常；踢人后两副本同时生效 |

## 9. 什么情况下推翻

- 平台演进为多租户 SaaS、QPS 上升一个量级 → 可引入 Redis 做会话共享，但「撤销即时生效」这条不变。
- 需要跨域单点登录（多个子产品共享登录态）→ 会话模型要重做（可能需要 OIDC）。

推翻流程同前：新开 ADR → 本 ADR 标 `Superseded` → 同步架构设计 §5/§8/§10、安全设计、TC-32。
