## 1. 背景

G6 原文是「**部署单元尽量少**」，判据是「一个方便部署的平台，不能先要求客户部署 6 套中间件」。

这条目标有三个问题：

1. **不可度量**：8 个算少还是 11 个算少？没有阈值，就无法验收，也无法据此做取舍。
2. **无法靠技术达成**：组件数量由功能决定（要状态就要库、要可靠就要队列、要告警就要规则引擎），不是选型能压缩的。
3. **与 G1/G2 硬冲突**：要可靠就得有队列、要对账就得有采集，这条冲突直接把 B1 逼成了「目标自相矛盾 · 最核心弊端」。

实际结果是：每次选型都要先过一遍「够不够轻」，导致 RabbitMQ 这类「团队能运维但更重」的选择被压后考虑——**这是用错误的判据在做决策**。

## 2. 决策

G6 改为：

> **G6 · 交付可控**：一次交付、可重复、失败可回滚。**组件数量不再作为约束**；但每新增一个**有状态**组件，必须同时具备四件事：离线安装、升级路径、备份恢复、自身监控。

## 3. 理由

1. **用户的真实痛点是「装不上、装很久、坏了没法回滚」，不是「组件有 9 个」**。前者是交付问题，后者只是实现细节。
2. **判据要能被验收**：「一条命令 + 可重复 + 可回滚」可以写成验收用例；「尽量少」不能。
3. **解除错误约束后，选型判据回到正确维度**：「团队能不能运维它」比「它占多少内存」更重要——这与 ADR-12 选 RabbitMQ 的逻辑一致，此前是矛盾的：一边因为「轻」推荐 JetStream，一边因为「能修」选 RabbitMQ。
4. **换来一个产品机会**：可观测性可以从「不得不精简的可选件」变成「开箱就有」的卖点。

## 4. 影响

| 对象 | 变化 |
| --- | --- |
| 架构设计 §1.1 | G6 重写；G1/G2 与 G6 的「最主要张力」表述改为「交付成本与运维负担」 |
| 权衡分析 B1 | 从「目标自相矛盾 · 最核心弊端」降级为「**成本转移**：管理面自身成为需要被运维的对象」——不再是设计错误，而是显性、可管理的成本 |
| 风险矩阵 | B1 保留（概率高、影响高），处置从「锁定最小部署单元」改为「一体离线包 + 可观测性可选装配 + 明确适用下限」 |
| D11 适用下限 | 依据从「投入产出比（组件多就不划算）」改为「**客户运维能力是否匹配**」；建议值不变，但不再由组件数推导 |
| D3 / D4 / D5 | 解除「必须最轻」约束：镜像仓库、日志、监控栈按「装得下去 + 团队能运维 + 生态成熟」评估，不以资源占用为第一判据 |
| 已定选型 | **不变**。G1/G2/G3/G5 不变，技术栈 7 项与 RabbitMQ 不变 |

## 5. 新增的约束（放宽不等于不管）

G6 放宽的是**组件数量**，不是交付质量。仍然强制：

- 管理面必须能以**一体离线包**交付，一条命令启动，失败可回滚（原 D6 的要求保留并升级为硬指标）。
- 每新增有状态组件 → 四件套齐备才允许进入部署清单（离线安装 / 升级路径 / 备份恢复 / 自身监控）。
- **离线包体积与启动时间必须有上限**，否则「放开了」会滑向「什么都装」。具体阈值 **待定**：M0 实测出基线后再定（候选：压缩包 ≤2GB、冷启动 ≤10 分钟），未定前不写入结论。

## 6. 风险

| 风险 | 缓解 |
| --- | --- |
| 放宽后组件持续膨胀，交付包越来越重 | 体积/启动时间上限 + 四件套门槛；每次新增组件走 ADR |
| 用「反正 G6 放开了」来为不必要的组件背书 | 新增组件必须回答「不加它，哪个验收指标会不达标」 |
| 目标客户其实是「3 台机器 10 分钟装完」的小场景 | 若该场景成为主战场，本 ADR 应被推翻（见 §7） |

## 7. 什么情况下推翻

- 目标客户明确要求「小规模、极简部署」，且组件数直接决定能否成单。
- M0 实测发现离线包体积/启动时间无论如何都超出可接受范围。

推翻流程同 ADR-11 / ADR-12：新开 ADR → 本 ADR 标 `Superseded` → 同步架构设计 §1.1、权衡分析 B1 与风险矩阵、PRD R4、项目计划 M0 与 RK-1、`AGENTS.md` I14。
