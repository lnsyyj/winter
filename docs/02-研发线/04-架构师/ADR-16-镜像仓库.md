## 1. 背景

ADR-15 留下两个镜像分发选项：走 registry，或 Nginx 提供静态 tar。本次确定：

- **只在管理平台部署镜像仓库**，不自建第二套；
- **所有镜像拉取统一走该仓库**，节点不再 `podman load` 静态 tar（tar 仅保留为应急降级）；
- **节点侧配置由 ansible 推送**（CA、仓库地址、只读凭据）。

引擎在 Harbor 与 `registry:2` 之间选 Harbor。

## 2. 决策

| 维度 | 决策 |
| --- | --- |
| 引擎 | **Harbor** |
| 位置 | 管理平台（与 Server / PG 等同机部署，MVP 单节点） |
| 认证 | **robot account（只读）**，按项目发放；管理员账号不发给节点 |
| 传输 | **TLS**，节点信任内部 CA；**不使用 `insecure-registry`** |
| 推送 | 仅从制包机 / CI 执行；节点只有 pull 权限 |
| 唯一性 | 所有镜像必须先入 Harbor 再被拉取，禁止节点直连公网 registry / docker.io |

## 3. 为什么是 Harbor

| 能力 | 为什么在本项目里是刚需 |
| --- | --- |
| **镜像 GC** | Ceph 镜像单版本 1~2GB，多版本并存时磁盘会持续膨胀；`registry:2` 没有 GC，只能手工清 |
| **漏洞扫描（Trivy）** | 管理面被攻破等于全部集群失陷（B2），镜像层是供应链最薄的一环 |
| **robot account** | 每节点组/每集群独立只读凭据，泄露可单独吊销，不必改全站密码 |
| **配额与项目隔离** | 平台镜像与 Ceph 镜像分项目，避免误删与混用 |
| 代价 | 多一个内部 Redis + Trivy 扫描器，离线包增大约 1GB；运维面更大 |

## 4. 关键约束

| 约束 | 原因 |
| --- | --- |
| **必须 TLS，配 `certs.d` 信任 CA** | `insecure-registry` 等于关掉校验，与 ADR-15 §4.2 是同一个投毒面 |
| **节点只发只读 robot 凭据** | 泄露后影响可收敛；push 权限只留在制包机 / CI |
| **Harbor 不得复用平台业务库** | 生命周期与备份策略不同，共用会把「平台库故障」与「仓库故障」绑死；用 Harbor 自带 PG 或独立实例 |
| **必须配保留策略 + 定期 GC** | 否则磁盘先满；GC 需要维护窗口，写入规则要写进运维手册 |
| **Trivy 漏洞库必须能离线更新** | 离线环境不导入漏洞库，扫描等于形同虚设——这条最容易被忘 |
| **节点不得直连公网 registry** | 否则供应链不可追溯，「镜像从哪来」无法审计 |
| **Harbor 自身镜像进 BOM** | 它也是被交付的组件，不能假设现场能拉到 |

## 5. 影响

| 对象 | 变化 |
| --- | --- |
| D3 | **关闭** |
| ADR-15 §4.1 | 静态 tar 方案从「并列选项」降为**应急降级路径**（Harbor 不可用时手工导入） |
| 部署资源 | 新增 Harbor（含 Trivy、内置 Redis）约 3C / 6G / 80G；管理面合计 ≈ **14C / 22G / 300G**（后续因审计独立库增至 15C / 24G / 350G，见 [ADR-29](ADR-29-审计落点.md)） |
| 安装手册 | BOM 增加 Harbor 与 Trivy 镜像；C4 改为「制包机 push → ansible 下发 CA/凭据 → 节点 pull」；**被管集群的 Ceph 镜像由每台节点的 cephadm 直拉，平台不预拉**（[ADR-30](ADR-30-镜像拉取方式.md)） |
| 测试 | 新增 TC-25（镜像供应链）：节点无外网只能从 Harbor 拉、吊销 robot 后 pull 失败、Harbor 停机不影响已运行容器 |
| V1 HA | Harbor 单节点在 V1 评估多副本 + 外部 PG/Redis；MVP 单节点可接受（ADR-10） |

## 6. 风险

| 风险 | 缓解 |
| --- | --- |
| Harbor 单点：挂掉后新节点起不来、滚动重启失败 | 已运行容器不受影响；节点保留本地镜像缓存；V1 做 HA |
| 磁盘被多版本镜像吃满 | 保留策略（每版本留 N 个）+ 定期 GC + 磁盘水位告警 |
| CA 分发失败导致 `x509` 报错 | ansible 在 C2 前置检查里验证 `podman pull` 探针，不通过就停 |
| Trivy 库离线陈旧，扫描失真 | 制包时同步漏洞库，版本写进 BOM |
| 有人顺手用 `--tls-verify=false` 绕过问题 | 视为违反 I15，评审拒绝；现场问题必须查 CA，不许关校验 |

## 7. 什么情况下推翻

- 镜像数量长期 < 5 且无扫描诉求 → 退回 `registry:2`。
- 客户已有 Harbor / ACR / Nexus → 改为对接客户仓库，我们只提供推送脚本与凭据模板。
- 管理面需要跨地域多活 → 改用 Harbor replication 或分布式仓库方案。

推翻流程同前：新开 ADR → 本 ADR 标 `Superseded` → 同步架构设计 §4.1/§6.1、部署资源表、安装手册、TC-25、`AGENTS.md` I15。
