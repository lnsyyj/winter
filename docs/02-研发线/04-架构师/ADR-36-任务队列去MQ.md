## 1. 背景

ADR-12 选 RabbitMQ 的前提是「Server 发布任务 → 队列 → 执行者消费」。但架构演进后这个前提没了：

1. **ADR-35 删掉了 Runner** —— 它曾是队列的唯一消费者；
2. **Agent 不连 MQ**（只与 Server 建 mTLS 长连接），队列没有第二个消费者；
3. 任务状态本来就在 PG `tasks` 表里 —— 于是**同一份事实有两个存放处**，靠对账维持一致。

结果：MQ 夹在 Server 与 Agent 之间多了一跳，却没人真正消费它。

## 2. 决策

| 项 | 决策 |
| --- | --- |
| 是否保留 MQ | **不保留**，删除 RabbitMQ |
| 队列载体 | PG `tasks` 表（**唯一真相**） |
| 派单 | `SELECT ... WHERE status='PENDING' AND next_retry_at<=now() ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 1` |
| 租约 | 派单时写 `leased_until` + `lease_owner`；心跳续租；超时未续 → 回收重派并 `attempt_count++` |
| 延迟重试 | `next_retry_at`，指数退避（1s→5s→30s→2min→10min） |
| 死信 | 状态值 `DEAD_LETTER`，不设独立死信队列；UI 提供「死信视图」 |
| 唤醒 | Agent 长连接时由 Server **内存推送唤醒**，兜底 1s 轻量轮询（`SELECT 1` 探测） |

## 3. 为什么可以去掉

| 原 MQ 承担的 | 现在的替代 |
| --- | --- |
| 持久化（重启不丢） | PG 本身持久化 + WAL |
| 重试 / TTL | `next_retry_at` + 退避策略 |
| 死信（DLX） | `status='DEAD_LETTER'` |
| 削峰 | 内部平台任务量低（峰值 <10 任务/秒），PG 足够 |
| 多消费者公平派发 | `SKIP LOCKED` 天然支持多副本 Server |
| 状态上报 | 本来就经 Server 写 PG，不经 MQ |

**最关键的好处**：状态只有一处。原来「MQ 里有消息但 tasks 表是 FAILED」这类漂移不可能再发生。

## 4. 必须实现的四个细节（缺一个就会出事）

| 细节 | 不做的后果 |
| --- | --- |
| **租约 + 续租** | Agent 拿到任务后崩溃 → 任务永远 RUNNING（僵尸） |
| **回收时 `attempt_count++`** | 无限重派同一个坏任务 |
| **`SKIP LOCKED`**（不是 `FOR UPDATE`） | 多副本 Server 互相阻塞，派单串行化 |
| **派单与状态迁移在同一事务** | 派单成功但状态没改成 RUNNING → 重复派发 |

## 5. 代价

| 代价 | 说明 |
| --- | --- |
| 自己实现投递语义 | confirm/ack/DLX/优先级都要用 SQL 与状态机重建，测试面变大（TC-40） |
| PG 写放大 | 每次状态迁移一次 UPDATE；高并发时行锁竞争 |
| 轮询开销 | 兜底轮询要足够轻（`SELECT 1` 探测 + 索引命中），否则空转打满 CPU |
| PG 成为任务单点 | PG 挂 = 任务停（原本 MQ 挂也停，实际差别不大） |
| 失去生态工具 | 没有 RabbitMQ 管理 UI 与 exporter，需自建队列深度指标（监控 `PENDING` 数量与最老任务年龄） |

## 6. 收益

- **少一个组件**：部署少一个容器、少一份 Erlang 运行时、少一处故障源；
- **资源下降**：2C / 2G / 20G，合计从 15C/24G/350G → **13C/22G/330G**；
- **离线交付更轻**：BOM 少一个镜像；
- **排障路径更短**：任务卡住直接看 `tasks` 表，不用「PG 说 A、MQ 说 B」。

## 7. 验收（TC-40）

| 场景 | 通过标准 |
| --- | --- |
| 并发派单 | 两个 Server 副本同时派单，同一任务不会被派两次 |
| 租约超时 | Agent 领了任务但不再续租 → 超时后回收重派，`attempt_count` 递增 |
| 重启不丢 | 派单后立刻重启 Server/Agent → 任务最终完成，不丢不重 |
| 延迟重试 | 瞬时错误后按退避时间重投，不早不晚 |
| 死信 | 超限任务进入 `DEAD_LETTER`，死信视图可见并可人工重跑 |
| 队列深度指标 | `PENDING` 数量与最老任务年龄可观测、可告警 |

## 8. 什么情况下推翻

- 任务量上升一个量级（>50 任务/秒）或 PG 锁等待显著 → 引入 MQ，但**只做投递**，状态仍以 PG 为准。
- 需要跨地域任务分发 → 需要独立的跨域传输层，PG 不合适。
