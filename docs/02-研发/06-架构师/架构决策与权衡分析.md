# Ceph 管理平台 · 架构设计理由、优点、缺点与弊端（v0.1）

| 项目 | 内容 |

| 文档归属 | 架构师（Architect）· 技术评审输入 |
| 状态 | 草案 · 用于拍板，不用于宣传 |
| 版本 / 日期 | v0.1 / 2026-11-07 |
| 配套 | [PRD](../../01-产品与设计/01-产品经理/PRD-Ceph管理平台.md) · [架构设计](./架构设计-Ceph管理平台.md) |

> **一句话结论**：这是一套「**控制面 / 数据面分离 + 异步任务 + 节点 Agent**」的稳妥架构，最大优点是平台挂了业务不挂；最大代价是**为了让运维变简单，先引入了一整套需要被运维的新系统**；最需要警惕的弊端是**高权限 Agent 把一次管理面入侵放大成全部集群失陷**，以及**平台状态与 Ceph 真实状态的永久漂移**。

> 本文严格区分三个词：
> - **理由** = 为什么这么选（§2）
> - **缺点** = 明知要付出、但可接受的**成本/代价**（§4）
> - **弊端** = 结构上难以根治、会长期反噬的**副作用**（§5）

## 1. 需求 → 设计映射

| 设想图里的诉求 | 架构中的落点 | 满足程度 |
| --- | --- | --- |
| 后台操作可视化 | React 控制台 + 任务进度/日志 + Grafana 面板 | 好 |
| 方便运维部署 | 向导式建集群 + 离线制品 + 复制粘贴级手册 | **中等，存在自相矛盾**（§5 B1） |
| 纳管已有集群 | 凭据导入 + 只读分级 `managed / limited` + 状态同步 | **偏弱，是最大承诺风险**（§5 B7） |
| 新建集群 | 异步 DAG：precheck → ansible → cephadm → OSD → 验收 | 好 |
| 多集群 / Region / AZ / Cluster | 三级元数据模型 + 无状态 Server | 逻辑上满足，**物理语义不足**（§5 B10） |
| 用户管理 / 权限 | RBAC + 三级作用域 | 好（但 Grafana 有旁路，§5 B9） |
| 操作审计 | 全量只追加载荷 + 前后状态快照 | 好（但 SSH 旁路，§5 B11） |
| 监控 / 告警 / 日志 | VM + vmalert + Alertmanager + Grafana + 日志系统 | 中等（生态错配，§5 B8） |
| 队列 / 数据库 / 仓库待选型 | 给出推荐与不选理由（架构设计 §4） | 待拍板（§8） |

## 2. 逐条设计理由

### R1 · 控制面与数据面分离（对应 ADR-01）

- **决策**：平台只做「看、管、记」，客户端 RBD/RGW/CephFS 的 IO 直连 Ceph，代理层一概不加。
- **理由**：Ceph 的稳定性是业务生命线，而管理平台是**全新自研、最不成熟**的组件。把新组件放进 IO 路径，等于让最不稳定的部分决定业务可用性。分离后，平台可以放心迭代、重启、甚至推倒重来。
- **放弃了什么**：无法做 IO 级的限流、审计、加密网关、多租户 QoS；也无法做「客户端 → 平台 → Ceph」的统一入口。
- **如果不这么做**：一次控制台发布事故 = 全部存储业务中断，这类事故对基础设施软件是致命的。

### R2 · 所有变更异步任务化（ADR-02）

- **决策**：`POST` 只返回 `task_id`，真实执行走队列 → Agent，进度用 WebSocket 推。
- **理由**：`cephadm bootstrap`、加 OSD、扩容都是分钟级甚至小时级操作，还伴随磁盘、网络等不可控外部因素。同步 HTTP 调用必然遇到超时、连接断开、重复提交，且无法做「失败步骤重试」。异步化同时天然产出**任务日志与审计载体**。
- **放弃了什么**：接口语义变复杂（要查任务状态）、前端要处理最终一致、要额外运维一套队列。
- **如果不这么做**：用户点一次「建集群」，浏览器转圈 20 分钟后超时，后台其实还在跑，用户再点一次 → 两个集群。

### R3 · Agent 拉模式 + mTLS，中心不直连 SSH（ADR-03）

- **决策**：Agent 主动连 Server 领取任务；Server 不持有到所有节点的 SSH 连接。
- **理由**：① 内网/跨机房常见单向防火墙与 NAT，中心直连往往不通；② 中心保存全部节点 SSH 私钥 = 一个文件泄露全集群；③ 连接风暴与并发 SSH 会话难以治理；④ 心跳天然提供节点在线状态。
- **放弃了什么**：要多部署和维护一个 Agent，且要解决 Agent 自身升级、证书轮换。
- **如果不这么做**：20 集群 × 25 节点的 SSH 连接池、密钥轮换、跳板机适配会成为长期泥潭。

### R4 · 双能力合并成「单二进制 + 双模式」（ADR-04）

- **决策**：保留 `system` / `ceph` 能力边界，但物理上同一个 Agent 二进制用 `--capability` 区分，能力白名单在 Server 侧下发。
- **理由**：草图里两个 Agent 都跑在被管节点、都需要 root/sudo 才能做事，**拆进程并没有真正缩小权限面**，却让部署单元、证书、心跳、升级、监控全部翻倍。真正的隔离来自「能执行哪些命令」，而不是「有几个进程」。
- **放弃了什么**：进程级的故障隔离（system 崩溃不会拖累 ceph 能力）、两类 Agent 独立升级节奏。
- **什么时候该拆回去**：当系统级操作需要常驻高权限守护、而 Ceph 级操作要跑在低权限账号时，进程隔离才有意义。

### R5 · cephadm 是「集群级执行器」，不是中心服务（ADR-05）

- **决策**：每套集群有自己的 cephadm 上下文（FSID / spec / 镜像版本），由该集群节点上的 Agent 驱动。
- **理由**：草图把 `cephadm` 画在中心并连向所有 node + 镜像仓库，容易被实现成「一个中心 cephadm 管全部集群」。但 cephadm 的状态是**按集群**的，中心化会导致跨集群 spec 串扰、凭据混合、单点故障，且和 Ceph 官方模型对抗。
- **放弃了什么**：无法用一个全局编排器统一下发跨集群变更（要靠任务层自己做批量）。
- **如果不这么做**：集群 A 的升级操作可能污染集群 B 的 spec，这是最难排查的一类事故。

### R6 · DB 只存元数据，Ceph 实际状态才是真相（ADR-06）

- **决策**：指标入 VM、日志入日志系统、PG 只存元数据/任务/审计；引入 Reconciler 定时对账，UI 以 `ceph -s` 实际状态优先。
- **理由**：把时序数据塞进 PostgreSQL 会迅速膨胀并拖垮业务库；而把 DB 里的「期望状态」当成真相展示，是运维平台最常见、也最危险的谎言。
- **放弃了什么**：跨指标 + 业务元数据的复杂关联查询要做二次聚合；页面要标注「数据时间」。

### R7 · 消息队列选 NATS JetStream（ADR-07）

- **决策**：必需组件，推荐 JetStream；团队已有 RabbitMQ 运维能力则选 RabbitMQ；**不选 Kafka、不选 Redis 当可靠队列**。
- **理由**：本平台要的是「持久化 + ACK + 重试 + 死信」的任务队列语义，不是日志流。Kafka 为这个规模引入过高运维成本；Redis 的持久化/确认语义不足以承载「不丢任务」的承诺；JetStream 单二进制、资源极轻，契合「少组件」目标。
- **放弃了什么**：Kafka 生态的流处理与重放能力、RabbitMQ 成熟的管理 UI。
- **风险**：团队不熟悉 NATS，出问题时排查经验少 → 若团队更熟 RabbitMQ，**选熟悉的那个比选先进的更重要**。

### R8 · 引入 Reconciler 主动对账（ADR-08）

- **决策**：平台默认假设自己的状态是过期的，定时用真实状态校准。
- **理由**：Ceph 会被平台之外的方式改变（运维 SSH、Ceph Dashboard、自动恢复、硬件故障）。**只要存在旁路，漂移就是必然**，不主动对账就只能在事故时发现。
- **放弃了什么**：额外的轮询开销与实现的复杂度。

### R9 · Grafana 经反代统一鉴权（ADR-09）

- **决策**：禁止用户直连 Grafana，所有查询经 Nginx 注入身份并按集群过滤。
- **理由**：Grafana 自带的数据源权限是全局的，直接嵌入等于给 `viewer` 开了「看所有集群指标」的后门，绕过平台 RBAC。
- **放弃了什么**：Grafana 原生用户体系与部分交互能力（编辑面板、探索页）。

### R10 · MVP 单机管理面，HA 延后（ADR-10）

- **决策**：MVP 允许 PG / JetStream / VM 单节点，V1 再做 HA。
- **理由**：G1 已经保证「管理面挂了业务不挂」，因此管理面 HA 的紧迫度显著低于功能闭环；先做 HA 会把 MVP 交付周期拉长、部署单元变多，与「方便部署」直接冲突。
- **放弃了什么**：MVP 阶段平台自身可用性约等于单机可用性（需明确写入 SLA，不能含糊）。
- **前提**：必须有备份与恢复演练，否则单机 = 元数据全丢。

## 3. 优点（相对「纯命令行 + 脚本」以及「中心直连 SSH」两种基线）

| # | 优点 | 具体收益 |
| --- | --- | --- |
| A1 | **数据面零影响** | 平台全组件停机、升级、回滚都不影响业务 IO，这是基础设施管理平台的首要美德 |
| A2 | 长操作可恢复 | 断点续跑、失败步骤重试、进度可见，30 分钟的建集群不再是黑盒 |
| A3 | 权限与审计内建 | 从第一天就有 RBAC 与只追加审计，而不是上线后补（补审计通常补不全） |
| A4 | 网络适应性强 | Agent 拉模式适配 NAT、单向放行、离线内网；中心无需全网 SSH 可达 |
| A5 | 多集群从模型层支持 | Region/AZ/Cluster 是数据模型而非页面筛选器，后续做批量、联邦不用重构 |
| A6 | 组件可替换 | 队列 / 监控 / 日志 / 仓库都有替代方案，接口分层清晰，无商业厂商锁定 |
| A7 | 部署形态轻 | Go 单二进制 + React 静态资源 + podman，无 JVM、无 K8s，适合私有化交付 |
| A8 | 与 Ceph 官方路径对齐 | 用 cephadm + podman，不 fork Ceph、不自建编排逻辑，升级与社区保持同向 |
| A9 | 增量演进 | MVP 单机 → V1 HA → V2 联邦，每一步不需要推翻前一步 |
| A10 | 兜底不丢失 | 保留 Ceph Dashboard 与 SSH，平台出问题时运维仍有路可走 |

## 4. 缺点（要付出的成本 / 代价，可接受但必须计入预算）

| # | 缺点 | 代价 | 应对 |
| --- | --- | --- | --- |
| D1 | 组件数量多 | DB + 队列 + VM + 日志 + Grafana + 仓库 + 反代，7 类有状态/半有状态组件 | 提供一体离线包；MVP 允许复用客户现有监控/仓库 |
| D2 | 自研面宽 | Web、Server、Agent、任务 DAG、对账、RBAC、审计、告警关联，几乎全自研 | 严格按 MVP 范围砍功能；优先复用 Ceph Dashboard |
| D3 | 多语言栈 | Go + TypeScript + Python(ansible/cephadm) + PromQL + Shell | 明确各语言边界，禁止在 playbook 里写业务逻辑 |
| D4 | 版本矩阵复杂 | OS × podman × Ceph × cephadm × Agent × Server 六层组合 | 维护兼容矩阵，CI 覆盖受支持组合 |
| D5 | 最终一致带来的体验成本 | 操作后页面不会立刻变化，用户会疑惑「点了没反应」 | 明确展示任务状态、进度与「最近同步时间」 |
| D6 | 监控栈自成一体的运维 | VM 规则、Grafana 面板、告警抑制都要维护 | 规则与面板纳入版本库，随平台一起发布 |
| D7 | 测试成本高 | 需要真实多节点 Ceph 环境做集成测试，纯 mock 测不出 cephadm 行为 | 建 3 节点常驻测试集群 + 场景化回归 |
| D8 | MVP 单点 | PG/队列单机，元数据丢失需从备份恢复 | 备份 + 恢复演练 + SLA 明示 |
| D9 | Agent 升级治理 | 500 个 Agent 的版本收敛、灰度、回滚 | 分批灰度 + 能力集协商 + 兼容 N-1 版本 |
| D10 | 文档与培训负担 | 私有化交付需要部署手册、操作手册、FAQ、验收报告 | 已按岗位拆分文档目录，由交付/支持岗位承接 |

## 5. 弊端（结构性副作用，难以根治，必须长期管理）

> 这一节是本文最重要的部分。以下每条尽量给出现象、根因、后果、缓解措施，并标明**能否根治**。

### B1 · 「为了简化运维，先制造了新的运维对象」——目标自相矛盾 ⚠️ 最核心

- **现象**：用户想「方便运维部署」，结果部署管理平台本身要先装 7 类组件；草图 TODO 里那句「细到复制粘贴就能部署上」正说明这个问题已经被感知到了。
- **根因**：通用管理平台天然需要状态、队列、指标、日志、鉴权；每解决一类问题就引入一类基础设施。
- **后果**：小规模场景（1～2 套集群）投入产出比为负，用户会觉得「还不如写个脚本」；私有化交付时，实施成本可能超过平台价值。
- **缓解**：把「管理面最小部署单元」当成 M0 的硬性指标；提供一体离线包；允许复用客户现有组件；**明确产品适用下限**（建议 ≥ 3 套集群或 ≥ 20 节点才划算）。
- **能否根治**：**不能**。只能靠产品边界与交付形态控制，不能靠架构消除。

### B2 · 高权限 Agent = 集中式 RCE 放大器 ⚠️ 最高安全风险

- **现象**：Agent 能跑系统级命令和 `ceph orch` 类命令，等价于在被管节点上持有 root。
- **根因**：管理能力来自执行能力，而执行能力必须落到节点上。
- **后果**：一旦 Server 被攻破（API 漏洞、凭据泄露、供应链投毒），攻击者可对**所有被纳管集群**下发白名单内的破坏性动作（删 OSD、改副本数、停服务），是「一次入侵、全量失陷」。
- **缓解**：mTLS + 任务签名 + 二次确认高危操作 + 白名单参数范围 + 网络分区 + 审计 fail-closed + 定期渗透测试；高危动作引入双人复核。
- **能否根治**：**不能**。只要平台能改集群，这条通道就存在；只能把爆炸半径压小（如按 Region 拆分控制面）。

### B3 · 双源真相漂移永远存在

- **现象**：控制台显示 `HEALTH_OK`，实际集群已 `HEALTH_WARN`；或任务显示成功但 Ceph 侧没生效。
- **根因**：平台 DB 是「期望状态 + 流程状态」，Ceph 是「真实状态」，中间隔着网络、CLI、人工旁路、自动恢复。任何对账都有窗口期。
- **后果**：运维基于错误展示做决策，是运维平台最易引发信任崩塌的问题。
- **缓解**：Reconciler 主动对账 + UI 以真实状态优先 + 显式采集时间 + 漂移告警 + 关键操作前后状态快照。
- **能否根治**：**不能**。只能缩短窗口、把不确定性显式化；禁止把 DB 状态当作真相。

### B4 · cephadm 抽象泄漏，平台在编排器之上又造了一个编排器

- **现象**：cephadm 自己有 spec、有 daemon 状态、有升级流程、有期望状态收敛；平台的任务 DAG 又在描述同样的事情。
- **根因**：cephadm 是声明式编排器，不是幂等命令库；平台把它当「命令执行器」用，两层期望状态会打架。
- **后果**：Ceph/cephadm 升级后，平台 DAG、参数解析、输出解析可能全部失效；spec 被平台外修改后，平台会「纠正」掉运维的合法改动。
- **缓解**：把 cephadm 交互收敛到薄适配层（版本适配 + 输出解析），DAG 只描述业务步骤；把 spec 变更纳入版本管理与漂移检测；每次 Ceph 大版本做兼容回归。
- **能否根治**：**不能**，除非改用 Ceph 官方 API 并放弃 cephadm，或改做纯声明式「只提交 spec」的模型。

### B5 · 长事务不可逆，「补偿」不等于「回滚」

- **现象**：建集群到第 5 步失败：MON 已起、OSD 已创建、数据盘已被占用，无法回到原点。
- **根因**：这些是对物理资源的操作，没有事务语义。
- **后果**：残留半拉子集群，只能人工清理；重试逻辑稍有不慎就重复添加 OSD。
- **缓解**：步骤幂等键 + 不可逆步骤标记 + 明确的「清理/重置」任务 + 失败即停不自动重试 + 人工确认入口。
- **能否根治**：**不能**。架构能做的是让失败可见、可续、可清理，而不是可回滚。

### B6 · 消息队列制造「恰好一次」的幻觉

- **现象**：网络抖动导致任务重复投递，Agent 重复执行 `ceph osd create`。
- **根因**：分布式系统只有「至少一次 + 业务幂等」，没有免费的 exactly-once。
- **后果**：重复 OSD、重复 Pool、配置被覆盖等真实损坏。
- **缓解**：`idempotency_key` 唯一索引 + Agent 本地执行结果缓存 + 执行前查询 Ceph 真实状态做前置守卫 + 非幂等步骤禁止自动重试。
- **能否根治**：**不能**，靠每一类任务单独设计幂等，是长期维护负担。**这是最容易被低估的工程量**。

### B7 · 「纳管已有集群」是产品承诺陷阱

- **现象**：草图写「可以纳管已有 ceph 集群」，但存量集群可能是 Rook、ceph-deploy、手工部署、不同大版本、不同认证方式，甚至网络不互通。
- **根因**：纳管需要的不只是凭据，还需要**一致的变更能力**；而变更能力取决于部署方式。
- **后果**：销售/内部承诺「什么集群都能管」，交付时发现只能看不能改，信任受损。
- **缓解**：PRD 已明确 `managed / limited` 分级与「非 cephadm 只读」；建立部署方式 × 版本 × 能力矩阵，把承诺写成矩阵而不是一句话。
- **能否根治**：**不能**，只能靠收窄承诺与清晰分级。

### B8 · VictoriaMetrics 与 Prometheus 生态的错配

- **现象**：草图写「告警集成 Prometheus 生态」，但用 VM 做存储。规则语法、函数支持、remote_write、Alertmanager 集成路径与原生 Prometheus 存在差异；Ceph mgr 的 prometheus 模块输出也随版本变化。
- **后果**：告警规则「看着像 Prometheus 但不完全生效」，静默漏报；Ceph 升级后指标名变化导致面板空白。
- **缓解**：vmalert 规则纳入版本库与 CI 校验；指标名映射单独维护；升级前跑指标回归。
- **能否根治**：可以，改用原生 Prometheus + Thanos，但会显著增加资源与组件数（与 G6 冲突）。**属于用成本换正确性**。

### B9 · Grafana 嵌入的权限旁路

- **现象**：Grafana 面板的数据源通常是全局只读，用户拿到面板 URL 就可能看到其他集群指标。
- **根因**：两套权限体系（平台 RBAC vs Grafana 数据源权限）。
- **后果**：RBAC 形同虚设，多租户/多客户场景直接不合规。
- **缓解**：Nginx 反代强制鉴权 + 按集群过滤查询 + 禁止直连 + 面板变量由平台注入。
- **能否根治**：可以，但会牺牲一部分 Grafana 原生能力；若客户要求强隔离，应改为平台自绘图表。

### B10 · 平台里的 Region/AZ 与 Ceph 的 CRUSH 故障域是两回事 ⚠️ 容易被忽视

- **现象**：平台把 3 个节点标成「跨 3 个 AZ」，用户以为数据跨 AZ 冗余，实际 CRUSH map 里它们仍在同一 `host` 或同一 `rack` 桶下。
- **根因**：Region/AZ 是**管理元数据**（自定义逻辑分组），CRUSH 是**数据放置规则**，两者没有自动同步。
- **后果**：平台给出了虚假的容灾安全感，这是比没有可视化更糟的情况。
- **缓解**：把 CRUSH map 的故障域层级只读映射到平台展示；建集群向导中显式要求配置 CRUSH rule / bucket，并做一致性校验；界面上区分「管理分组」与「数据故障域」两个术语。
- **能否根治**：可以，但需要在需求层就纠正概念，不能只靠架构。

### B11 · 审计覆盖不到 SSH 旁路

- **现象**：审计员查到「上周三无人操作 prod-cluster」，但运维其实 SSH 上去改了配置。
- **根因**：平台不是唯一变更通道，且按设计**必须保留** Ceph Dashboard / SSH 作为兜底。
- **后果**：合规场景下「全量操作审计」的承诺打折。
- **缓解**：审计表述改为「平台内操作 100% 留痕」；配合节点侧 auditd / 命令审计、堡垒机日志做交叉核对。
- **能否根治**：**不能**，除非收走 SSH（那又与兜底原则冲突）。

### B12 · 白名单与易用性的拉扯，会让平台被架空

- **现象**：为了安全只允许白名单任务，运维遇到白名单没覆盖的场景就绕开平台敲 SSH；久而久之平台只剩「看板」。
- **根因**：安全约束收敛了能力，而运维场景是长尾的。
- **后果**：平台价值被稀释，投入产出比进一步下降，回到 B1 的负循环。
- **缓解**：把「新增任务模板」做成低成本、可配置、可灰度发布的能力（模板即配置，不发版）；统计 SSH 旁路高频操作反哺模板库。
- **能否根治**：**不能**，这是组织与产品运营问题，不是纯技术问题。

### B13 · 规模扩大后的同步风暴与升级爆炸半径

- **现象**：20 集群 × 25 节点，每 30s 拉一次状态与指标，mgr / VM / DB 压力线性上涨；一次控制面升级影响全部集群。
- **缓解**：按集群分片 + 抖动（jitter）+ 分级同步频率 + 事件驱动补充；V2 按 Region 拆分自治控制面。
- **能否根治**：部分可，属于规模化必然成本。

### B14 · OS 与运行时基线的滚动风险

- **现象**：CentOS Stream 9 是滚动发行版，内核、podman、selinux-policy 的小版本更新可能让 cephadm / Ceph 容器行为变化。
- **根因**：Stream 位于 RHEL 之前，更新频繁且不像 RHEL 有严格的点版本冻结。
- **缓解**：锁定已验证的软件包版本快照 + 内网镜像源 + 升级前回归；若客户要求长期稳定，评估 Rocky/Alma 或 RHEL 作为第二基线。
- **能否根治**：可以（换基线），但会偏离草图设定，需产品决策。

## 6. 备选架构对比（为什么没选）

| 方案 | 做法 | 优点 | 不适合本项目的原因 |
| --- | --- | --- | --- |
| **A. 本方案**（控制面 + Agent + cephadm） | 异步任务、权限/审计内建 | 数据面隔离、多集群、可演进 | 组件多、自研面宽（§4/§5） |
| **B. 中心直连 SSH + Ansible/AWX** | Server 用 ansible 直接跑 playbook | 组件极少、上手快、幂等性好 | 密钥集中、无实时任务进度、跨网络受限、审计与 RBAC 弱；20 集群规模连接风暴 |
| **C. 直接用 Ceph Dashboard 二次开发** | 改 Ceph 自带 Dashboard | 与 Ceph 同版本、零适配 | 单集群视角，多集群 / 审计 / 权限模型要从零加；与 Ceph 版本强绑定，升级易冲突 |
| **D. Rook / Kubernetes 托管** | K8s Operator 管理 Ceph | 声明式、社区成熟、自愈强 | 引入整套 K8s 运维体系，与 G6 /「复制粘贴部署」直接冲突；存量非 K8s 集群无法纳管 |
| **E. ceph-mgr RESTful / Python 模块 + 轻前端** | 用 Ceph 原生 API | 组件少、无 Agent | 系统级操作（OS 初始化、磁盘、podman）仍需要节点执行通道；API 覆盖度随版本波动；多集群编排仍要自研 |
| **F. 无 Agent、Server 内嵌执行器** | 中心进程直接调 cephadm | 部署单元最少 | 把 cephadm 中心化（见 R5），凭据与网络问题全部回到中心；单点即全局不可管 |

> 若目标规模其实只有 1～2 套集群，**方案 B 或 C 更划算**。本方案的有效性建立在「多集群 + 多操作者 + 需要审计」这个前提上；PRD §11.3 的问题 2 必须先回答。

## 7. 什么时候应该推翻这套架构

出现以下任一信号，应重新做架构决策，而不是继续打补丁：

1. 目标规模 > 100 集群 / 数千节点，单控制面同步与队列成为瓶颈 → 转多 Region 联邦或分层控制面；
2. 需要接管数据面（IO 限流、加密网关、多租户配额）→ R1 不再成立，需重新评估代理层；
3. 组织已全面 K8s 化，且存量集群可迁移 → 重新评估 Rook；
4. 平台自身 SLA 要求 > 99.9% 且不能接受计划内停机 → 需要真正的多活控制面，成本结构完全不同；
5. 客户环境禁止安装任何 Agent → 只能退回方案 B/E，同时接受审计与网络能力的降级；
6. 安全评估判定「不允许任何组件持有节点级命令执行权限」→ 平台只能做只读 + 生成可执行脚本。

## 9. 如果只能先做三件事

1. **M0 先手工跑通一次完整建集群**：在离线 CentOS Stream 9 + podman 环境下，用纯命令把 3 节点集群建到 `HEALTH_OK`。若这一步都不稳定，任何平台化都是在自动化一个不可靠的过程。
2. **把「最小部署单元」当成硬指标**：管理面一体离线包 + 复制粘贴命令，先于任何新功能。这直接决定 B1 是否会把项目拖死。
3. **安全边界与幂等规范先写死再写业务**：mTLS、任务签名、白名单模板、幂等键、审计 fail-closed。这些事后补的代价是重写整个任务层。

> 最后提醒一句：这套架构里，**技术难点不在 React 或 Golang，而在「不可逆、不幂等、会漂移的物理世界操作」**。把 80% 的设计精力放在任务层、对账层和安全边界上，比画更多组件图有价值。
